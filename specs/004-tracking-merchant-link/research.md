# Research: Tracking Page, Merchant Link, and WhatsApp Message

Phase 0 of [plan.md](plan.md). The toolchain, monorepo layout, client–server contract, and
design system are fixed by [feature 001's research](../001-shipment-registration/research.md);
statuses, custody, stops, photos, and settings by features
[002](../002-routes-dispatch/research.md) and [003](../003-courier-app/research.md).

## R1. Where the public pages live

- **Decision**: two routes of the existing web app, `/seguimiento/$code` (tracking page) and
  `/cliente/$code` (merchant page), each loaded as its own lazy chunk so a recipient
  downloads only what the page needs. The service worker of feature 003 is registered only
  outside these routes, so recipients never download the app shell of the panel or the
  courier app.
- **Rationale**: the constitution ratifies one web app serving the tracking page; FR-013 and
  SC-003 (readable within 3 s on a slow connection) are met by code splitting, not by a
  second rendering stack.
- **Alternatives considered**: server-rendered HTML from Hono (fastest, but a second way to
  build screens and apply the design system); a separate `apps/tracking` (a second build
  and deploy).

## R2. Secret codes

- **Decision**: 128 random bits from `crypto.randomBytes(16)` encoded as base64url (22
  characters), generated by the server: `shipments.tracking_code` when a shipment is
  created (single and bulk), and `merchants.link_code` when a merchant is
  created or its link is replaced. Both columns are unique and stored in plain text, because
  the dispatcher copies the links again later.
- **Rationale**: FR-002, FR-021, Constitution IX ("unguessable random tokens, never
  sequential identifiers"). With 128 bits, trying links cannot find one (SC-005). The
  8-character tracking number (40 bits) stays a human reference, not a secret (feature 001,
  R6).
- **Alternatives considered**: signed tokens (a key to rotate for no gain); hashing the codes
  (links could not be shown again).

## R3. What a public page may show

- **Decision**: one pure function in `packages/domain/src/public-tracking.ts`,
  `publicTrackingView(shipment, context, now)`, returns exactly the fields of FR-003–FR-008,
  FR-010, and FR-014 for each status and kind: public status text (FR-005), reason text,
  "entregas antes de la tuya", courier's first name and phone (only when FR-007 allows), COD
  amount to pay, expiry. The public endpoint serializes only its result. A second function,
  `merchantShipmentView`, does the same for the merchant page (FR-019, FR-020).
- **Rationale**: SC-004 is verified by unit tests over every status and kind; nothing can
  leak by adding a column to a query (Constitution III and IX).

## R4. "Entregas antes de la tuya"

- **Decision**: `deliveriesBefore(stops, shipmentId)` in `packages/domain/src/routes.ts`
  counts pending delivery and return stops placed before the shipment's pending delivery
  stop in the route's order (before its pending pickup stop for a reverse pickup not yet
  picked up).
- **Rationale**: FR-006 with the stop order of feature 002; completed stops are skipped
  whatever their position (EC-06).

## R5. Expiry

- **Decision**: the tracking view is complete while the shipment is not final, or until 7
  days after the `occurred_at` of the event that made it `delivered`, `returned`, or
  `voided`; after that the endpoint returns only `{ expired: true }` and the support
  contact. A revert (feature 003) makes it current again with no extra data.
- **Rationale**: FR-010 (clarification Q2); computed from the existing event history, no
  new column.

## R6. Abuse protection

- **Decision**: a fixed-window limit of 60 requests per minute per client address on
  `/api/public/*`, kept in memory in `apps/server/src/lib/rate-limit.ts`; a limited request
  gets `429` with a Spanish message. The client address is the value of
  `X-Forwarded-For` set by Caddy, which replaces any value sent by the client (no trusted
  proxies configured); the server listens only on the internal Docker network, so every
  request passes through Caddy. Unknown, deactivated, and replaced codes all return the same `404`.
  Public responses carry `Cache-Control: no-store` and `X-Robots-Tag: noindex`, and the
  public web routes are served with `X-Robots-Tag: noindex`.
- **Rationale**: FR-011, FR-012. One server process (Principle I) makes an in-memory counter
  correct.
- **Alternatives considered**: a rate-limit package (a dependency for 20 lines); a shared
  store such as Redis (a second process for one counter).

## R7. Link previews

- **Decision**: `index.html` keeps a static title "Domy" and a generic description and
  image, with no per-shipment tags.
- **Rationale**: FR-012 and EC-10: chat previews read the HTML without running scripts, so a
  single-page app shows only the static tags by construction.

## R8. The WhatsApp message

- **Decision**:
  - `composeMerchantMessage(merchant, shipments, baseUrl)` in
    `packages/domain/src/merchant-message.ts` builds the Spanish text: a greeting with the
    merchant's name, one entry per shipment (recipient, neighborhood, tracking number, link),
    and the merchant link; above 20 shipments, the count and the merchant link only.
  - "Enviar por WhatsApp" opens `https://wa.me/57{phone}?text={message}` in the same tap,
    so the browser does not block it; "Copiar mensaje" uses the clipboard. In both cases the
    page then sends `POST /api/notifications` with an `actionId`, retried until it
    succeeds.
  - A notified shipment gets `notified_at` and `notified_by` and a `notified` shipment event.
- **Rationale**: FR-015–FR-018, decision #9, SC-001. The message is built in the browser
  from data the list already has, so opening WhatsApp needs no round trip.
- **Limits**: the message with 20 entries is about 2,500 characters, within what WhatsApp
  accepts in a link.
- **Alternatives considered**: WhatsApp Business API (automatic sending is Phase 3); marking
  as notified only after the dispatcher confirms it was sent (a third tap for every
  merchant).

## R9. Refresh and speed

- **Decision**: the tracking page refetches every 30 seconds while visible (TanStack Query);
  the merchant page every 60 seconds. The Playwright test loads the tracking page with the
  network throttled to a slow mobile profile and requires the status visible within 3
  seconds.
- **Rationale**: FR-013, SC-002, SC-003.

## R10. Photos on the merchant page

- **Decision**: `GET /api/public/merchant/:code/photos/:photoId` streams the object from the
  storage of feature 003 after checking that the photo belongs to a shipment of that
  merchant; there is no other public way to reach a photo.
- **Rationale**: FR-020, FR-022; business master §4.5 (photos only on the merchant link).

## R11. Settings and privacy

- **Decision**: `company_settings` (feature 003) gains `support_phone` and `company_name`
  (default "Cohex"), edited by the owner on the settings page. Couriers' first names and
  phones are shown to recipients (decision #8); the couriers' authorization for this use
  of their data MUST be collected before go-live (Constitution VII, v1.2.0; Ley 1581 de
  2012) and is part of the go-live checklist.
- **Rationale**: FR-009; Constitution IX.
