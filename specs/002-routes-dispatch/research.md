# Research: Routes and Dispatch

Phase 0 of [plan.md](plan.md). The toolchain, monorepo layout, client–server contract,
authentication, testing strategy, and design system are fixed by
[feature 001's research](../001-shipment-registration/research.md) and are not repeated here.
Versions verified against the npm registry on 2026-09-30.

## R1. Route structure: stops and tasks

- **Decision**: a route has ordered **stops**; each stop has one or more **tasks**, one per
  shipment handled there. A pickup stop groups the pickup tasks that share a pickup address;
  a delivery stop has one delivery task; an errand stop has one errand task. A stop is
  completed when none of its tasks is pending; route progress counts completed stops.
- **Rationale**: FR-005 needs "pick up N shipments here" as one stop, while feature 003
  needs to complete shipments one by one (a package may not be ready at a pickup). Tasks
  give that granularity without changing the stop list the dispatcher orders.
- **Alternatives considered**: one row per shipment and kind, grouping pickups only in the
  UI (ordering and "empty pickup stop" rules become ambiguous); stops without tasks (cannot
  represent a partially completed pickup).

## R2. Route rules as pure functions

- **Decision**: `packages/domain/src/routes.ts` holds pure functions over plain data:
  `buildStops`, `addShipmentToStops`, `removeShipmentFromStops`, `moveStop`,
  `validateStopOrder` (a delivery stop stays after the pickup stop of its shipment; completed
  stops do not move), `isRouteFinished`, and `routeProgress`. The server loads the route,
  applies a function, and saves the result in one transaction; the web app uses the same
  functions to preview and validate a drag before sending it.
- **Rationale**: Constitution III and VI: one tested implementation of the ordering and
  grouping rules, shared by server and browser.
- **Alternatives considered**: ordering logic in SQL (hard to test and to reuse in the
  browser); validation only on the server (the drag would appear to work and then jump
  back).

## R3. Drag and drop

- **Decision**: `@dnd-kit/core` 6.3 with `@dnd-kit/sortable` 10 for reordering stops.
- **Rationale**: FR-006 requires dragging and keyboard reordering; dnd-kit provides pointer,
  touch, and keyboard sensors with screen-reader announcements (WCAG 2.2 AA), which the
  native HTML drag-and-drop API does not. It is the library shadcn/ui's own sortable examples
  use.
- **Alternatives considered**: native HTML5 drag and drop (no keyboard or touch support);
  `@dnd-kit/react` 0.5 (pre-1.0); up and down buttons only (slower for nine stops, kept as
  the keyboard path through dnd-kit).

## R4. Exactly-once actions

- **Decision**: every mutating request carries `actionId`, a UUID generated by the client.
  The server stores it in the first event the action writes (`route_events.client_event_id`,
  unique and optional; an action that writes several events leaves it null on the rest). A
  request whose `actionId` already exists returns the current route with `200` and does
  nothing else. Route creation also carries the route `id`. Requests additionally carry the
  route `version` for concurrency (R5).
- **Rationale**: Constitution II ("every mutation sent by a client MUST carry a
  client-generated UUID… exactly one effect") and FR-020. Storing the key on the event means
  no extra table and the same mechanism the courier app will use.
- **Cross-feature alignment**: feature 001 protected edits only with `version`, which
  prevents a double effect but reports a conflict to a user who merely retried. Its contract,
  data model, spec FR-042, and tasks are updated in this branch to carry `actionId` on every
  mutation as well (`shipment_events.client_event_id` and a new
  `audit_events.client_event_id`).
- **Alternatives considered**: a separate idempotency-key table with stored responses (more
  machinery than needed); `version` alone (retries surface as false conflicts).

## R5. Concurrency

- **Decision**: `routes.version` with optimistic checks, as for shipments (feature 001,
  R10). Any structural change (stops, courier, status) increments it; a stale version
  returns `409 version_conflict` and the editor reloads, keeping the dispatcher's pending
  selection.
- **Rationale**: FR-021 with the mechanism already in use.

## R6. One route in progress per courier

- **Decision**: a partial unique index on `routes (courier_id) WHERE status =
  'in_progress'`. Dispatching, undoing, and reassigning a whole route rely on it; a violation
  becomes `409 courier_busy` with the number of the courier's current route.
- **Rationale**: FR-009 and clarification Q2 enforced by the database (Constitution IV), so
  two dispatchers cannot dispatch to the same courier at once.
- **Alternatives considered**: a check in application code (race between two requests).

## R7. Shipment membership and custody

- **Decision**: `shipments.route_id` points to the route currently carrying the shipment
  (null while "Registrado"), which enforces "at most one active route" (FR-004) by
  construction. `shipments.custody_courier_id` records who holds the package: set at pickup
  (feature 003) and changed only by a confirmed handover.
- **Rationale**: FR-004, FR-025, SC-005. Two columns answer "where is it" and "who has it"
  without joins; the full history stays in events.
- **Alternatives considered**: deriving membership from the stops (no constraint protects
  against two routes); deriving custody from events on every read (slow and error-prone).

## R8. Handovers

- **Decision**: a `handovers` table with `pending`, `confirmed`, `cancelled`, at most one
  pending per shipment (partial unique index). On reassignment of a picked-up shipment the
  delivery task moves to the receiving route and is blocked by the pending handover.
  Confirmation (by the receiving courier in feature 003, or by the dispatcher on their
  behalf) sets custody and unblocks the task; cancellation moves the task back. When a whole
  route is reassigned, each picked-up shipment gets a handover within the same route.
- **Rationale**: FR-025 and clarification Q3; custody never changes without a confirmation.

## R9. Route status and the "Finalizada" rule

- **Decision**: status is stored (`draft`, `in_progress`, `finished`, `cancelled`) and
  recomputed inside every transaction that changes a task: a route in progress becomes
  `finished` when it has no pending task and no pending handover. Task statuses are
  `pending`, `completed`, and `failed` (a delivery exception, set by feature 003).
- **Rationale**: FR-012 and clarification Q1 (never closed by the clock). Storing the status
  keeps the one-in-progress index (R6) simple.

## R10. Removing stops and Constitution IV

- **Decision**: when a shipment leaves a route, its pending tasks and any stop left empty
  are deleted rows; completed and failed tasks are never deleted. The change is recorded in
  `route_events` with the full before and after.
- **Rationale**: Constitution IV forbids hard-deleting operational records (shipments,
  routes, events, collections). A pending task is part of a route's current arrangement, like
  a field of a shipment: changing it is an edit of the route, whose previous state lives in
  the append-only history. Keeping removed tasks as soft-deleted rows would complicate every
  query and the ordering rules for no gain in traceability.
- **Alternatives considered**: soft-deleted tasks (rejected above).

## R11. Route numbers

- **Decision**: `number` is the next integer for the route's service date, assigned in the
  creation transaction and protected by a unique index `(service_date, number)` with retry.
  Cancelled routes keep their number.
- **Rationale**: FR-002; short and sayable ("Ruta 3").

## R12. Board data

- **Decision**: one endpoint returns the routes of the date, the routes in progress from
  earlier dates, the unassigned count, and `serverTime`; the web app polls it every 20
  seconds with the shipment board (feature 001, R9). Flags per route are computed with the
  existing `shipment-flags` module.
- **Rationale**: FR-018, SC-003, same freshness mechanism as feature 001.

## R13. Performance budget and hardening

- **Decision (performance)**: on a busy day over a long history (100,000 earlier shipments,
  40 routes of 15 shipments, 200 shipments without a route), the routes board, "Sin
  asignar", a route's detail, and a shipment's detail each answer in under 500 ms, and
  creating, ordering, and dispatching a route of 15 shipments each take under 1 second,
  measured against real PostgreSQL in `apps/server/tests/routes-scale.test.ts`.
- **Rationale**: the board polls every 20 seconds (R12) and every open panel adds to that
  load; a dispatcher's action must feel immediate to build a route in under 2 minutes
  (SC-001). The limits leave room for slower CI machines.
- **Decision (hardening)**: every answer carries Hono's secure headers, with framing denied
  (`X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'`), `nosniff`,
  and `Referrer-Policy: strict-origin-when-cross-origin`. Request bodies under `/api` are
  limited to 1 MB (`413 payload_too_large`), a body that cannot be parsed answers
  `400 invalid_request` instead of a server error, and a request carries at most 200
  shipment identifiers. Mutations take only `application/json`, so with the `SameSite=Lax`
  session cookie no cross-site form can post them. A content security policy for scripts and
  styles waits for the production deployment, where it can be tested against the built app.
- **Rationale**: Constitution V and IX; the security test (T059) found a broken JSON body
  answered with `500`, no limit on bodies or lists, and no protective headers.
