# HTTP API Contract: Courier App

Extends the contracts of [feature 001](../../001-shipment-registration/contracts/http-api.md)
and [feature 002](../../002-routes-dispatch/contracts/http-api.md) and follows their
conventions: JSON under `/api`, Zod schemas from `packages/domain` (`schemas/courier.ts`),
session cookie, integer COP, Spanish error messages, no `DELETE` endpoints, `actionId` on
every mutation.

## Conventions added by this feature

- **Records** (FR-019): a courier record carries its own `id`, generated by the client; it
  is the idempotency key. Sending it again returns its stored outcome.
- **Time**: each record carries `occurredAt` (client clock) and the request carries
  `deviceNow`; the server stores `occurredAt` corrected by its offset to `deviceNow`.
- **Never refused for state** (FR-024): a well-formed record is always stored. The response
  says what happened to it: `applied`, `duplicate`, or `not_applied`.
- **Limits** (feature 002, research R13): every body is limited to 1 MB, so a photo above
  1 MB is refused with `413 payload_too_large`; a request carries at most 50 records.

| Status | `code` | When |
| --- | --- | --- |
| 409 | `no_exception_to_decide` | Deciding for a shipment that is not in "Novedad"; a return already decided accepts only a change to `new_attempt` (FR-029) |
| 409 | `not_held_by_courier` | "Recibido en oficina" for a package no courier holds (FR-041) |
| 409 | `record_not_revertible` | Reverting a record that is not the shipment's latest applied delivery, exception, or return, or a package record followed by another dispatch decision or custody change (FR-035) |
| 409 | `office_not_configured` | "Recibido en oficina" before the office address is set (FR-041) |
| 422 | `occurred_in_future` | A record on behalf with `occurredAt` later than now (FR-034) |

## Courier endpoints (role: courier)

| Method and path | Request → Response |
| --- | --- |
| `GET /api/courier/route` | → `CourierSnapshot` = `{ serverTime, sessionExpiresAt, route: CourierRoute \| null, handoversToGive: HandoverToGive[], heldOffRoute: HeldShipment[], notices: Notice[], summary: DaySummary }`; `DaySummary` (today, Bogotá) = counts of deliveries, exceptions, returns, pending stops; `cash`, `companyTransfer`, `merchantTransfer`, `disbursements`, `cashToHandOver` (FR-037). `CourierRoute` = number, service date, `stops` in order, each with kind, address, neighborhood, contact phone (the recipient's on a delivery stop; the merchant's `whatsappPhone` on a pickup or return stop; absent when not registered, FR-016), and `tasks` (shipment id, tracking number, merchant, recipient name and phone, carrier, destination town, errand description, instructions, package count and size, delivery window, COD amount, status, `blockedByHandover`, `problemNote`; the phone computes the at-risk or late flag from the window and its corrected clock, so it stays right without signal). Updates `couriers.last_synced_at`. An account not linked to a courier gets `403` (FR-005, FR-022, FR-028) |
| `POST /api/courier/records` | `{ deviceNow, records: CourierRecordInput[] }` (1–50, in the order they happened) → `{ results: { id, outcome }[] }`. Each record is applied in its own transaction (FR-018–FR-026) |
| `PUT /api/courier/photos/:id` | Body: the JPEG image (`image/jpeg`, ≤ 1 MB, else `413 payload_too_large`) → `204`. `404` while its record has not arrived; repeating it is harmless (FR-023) |
| `POST /api/courier/notices/acknowledge` | `{ actionId, noticeIds, occurredAt }` → `204`; sets `acknowledged_at` only where empty (FR-027) |
| `GET /api/courier/push-config` | → `200 { publicKey: string \| null }`; the server's VAPID public key, or `null` when phone notifications are disabled in development. Requires a linked courier account like the snapshot; owner, dispatcher and unlinked courier get `403`. Never returns the private key or subject (FR-040, owner-approved US5 alignment) |
| `POST /api/courier/push-subscriptions` | `{ actionId, endpoint, keys: { p256dh, auth } }` → `204` (FR-040) |
| `POST /api/courier/push-subscriptions/remove` | `{ actionId, endpoint }` → `204` |

`CourierRecordInput` is a union by `kind`; every member has `id`, `shipmentId`, `occurredAt`,
and optional `location: { latitude, longitude, accuracyM }`:

| `kind` | Extra fields |
| --- | --- |
| `pickup` | — |
| `delivery` | `receivedByName`; `cashAmount`, `companyTransferAmount`, `merchantTransferAmount` (default 0); `note` (required when the total differs from the COD amount); `photos: { id, kind: 'proof' \| 'transfer_receipt' }[]` (at most 3 `proof`) |
| `exception` | `reason`; optional `note`; `photos` of kind `exception` |
| `problem` | `note` (5–200 characters) |
| `return` | `receivedByName`; `photos` of kind `proof` |
| `disbursement` | `amount` (> 0), `payee`, optional `note`; `photos` of kind `disbursement_receipt` |
| `handover_confirmation` | — |

## Dispatch panel endpoints (roles: owner, dispatcher)

| Method and path | Request → Response |
| --- | --- |
| `POST /api/shipments/:id/records` | A `CourierRecordInput` without `shipmentId` (any kind except `handover_confirmation`, which feature 002 provides), plus optional `occurredAt` (default now). Stored with `on_behalf = true` for the courier who holds the shipment or whose route carries it → `{ id, outcome }` (FR-034) |
| `POST /api/shipments/:id/exception-decision` | `{ actionId, decision: 'new_attempt', serviceDate?, routeId? }` or `{ actionId, decision: 'return', routeId? }` → `200 Shipment`; with `routeId`, the stop is added under the rules of feature 002 (`409 route_not_in_progress`, handover when another courier's) (FR-029). A replay of an accepted `actionId` returns the current shipment without reapplying the decision, even after a subsequent change |
| `POST /api/shipments/:id/office-receipt` | `{ actionId }` → `200 Shipment` with `heldAtOffice: true` on first receipt (FR-041). A replay of an accepted `actionId` returns the current shipment without receiving custody again, including after the courier has picked it up from the office |
| `POST /api/shipments/:id/clear-review` | `{ actionId, note }` → `Shipment` (FR-026) |
| `POST /api/courier-records/:id/correct` | `{ actionId, reason, receivedByName?, cashAmount?, companyTransferAmount?, merchantTransferAmount?, exceptionReason?, note?, amount?, payee? }` → `CourierRecord` (FR-035) |
| `POST /api/courier-records/:id/revert` | `{ actionId, reason }` → `Shipment` (FR-035) |
| `GET /api/photos/:id` | → the image. Owner and dispatcher: any photo; courier: photos of their own records. `404` when the object was deleted by retention (FR-036) |
| `GET /api/settings` | No request body → `200 CompanySettings`; owner and dispatcher (FR-041) |
| `PATCH /api/settings` | `{ actionId, officeAddress, officeNeighborhoodId }` → `200 CompanySettings`; owner only, change audited (FR-041). Replaying an accepted `actionId` returns the current configuration without restoring an intervening change |

`CompanySettings` reuses `packages/domain/src/schemas/courier.ts`:
`{ officeAddress: string | null, officeNeighborhood: { id: string, name: string } | null }`.
Both fields are null before the office is configured, even when the singleton row has
not yet been created. After PATCH, both are populated; `officeNeighborhood` resolves
the submitted neighborhood id to its name. Neither response includes `actionId` or
uses the input field `officeNeighborhoodId`. A dispatcher PATCH or a courier GET/PATCH
returns `403 forbidden`, under the existing authentication conventions.

Concurrent or late repeats of an accepted exception decision produce no additional
decision event, route task, handover, custody change or fee change. Remember the action
and all its effects in the same transaction, and recognize a replay before applying
current-state guards (Constitution II, IV). Settings use the shared `auditedChange`
receipts, including unchanged edits, so those replays cannot overwrite a newer value.

Reasons and notes are 5–200 characters.

For `POST /api/courier-records/:id/revert`, an applied errand completion uses the
owner-approved exception to the package rule (FR-007, FR-035): `dispatched` with the
errand task pending if the original record's route is still `in_progress` with the
same courier; otherwise `registered` with no route. Neither outcome creates courier
or office custody. The record stays with its revert author/time/reason and stops
contributing to attempts/collections like any reverted delivery. Service date is kept.
For packages, a subsequent dispatch decision or custody movement makes the revert
`409 record_not_revertible`, even without a newer delivery/exception/return. Refusal
changes no record, shipment, task, custody, event or notice. Replaying an already accepted
revert is still recognized before this guard and does not undo any intervening operation.

## Changes to the contracts of features 001 and 002

- **`GET /api/couriers`**: each courier gains `account: { id, email } | null` (FR-002).
- **`PUT /api/couriers/accounts/:userId`** (owner only, new): `{ actionId, courierId | null }`
  → `{ courier: Courier | null }`. Links the account to the courier, or unlinks it, in one
  transaction: the account leaves its previous courier and replaces the courier's previous
  account, with an audit event per courier changed. `409 courier_account_invalid` for an
  account that is not an active courier account or a courier that is deactivated; `404` for
  an unknown account or courier (FR-002).
  Every accepted `actionId` is remembered, including an unchanged link or unlink. Such a
  request writes an `updated` audit receipt with empty `changes`, for the courier when
  linked or the user when already unlinked, without updating the courier. A replay returns
  the current link and cannot undo an intervening change (Constitution II).
  These receipts use the shared `auditedChange` mechanism of feature 001's master data.
  `GET /api/audit-events` excludes empty-change receipts from the owner's history.
- **`POST /api/auth/admin/set-role`**: `409 courier_account_linked` when a linked courier
  account would stop being a courier; it is unlinked first (FR-002).

- **`GET /api/shipments/:id`**: gains `records: CourierRecord[]` (with `outcome`, `onBehalf`,
  photos and their `uploaded` state, revert data) and `recordFlags`, then `attempts`,
  `heldAtOffice`, `returnDecided`, `needsReview` (FR-036).
- **`GET /api/shipments/board`**: each shipment gains `recordFlags`, a list of
  `no_photo`, `photo_pending`, `collection_differs`, `pickup_problem`, and `needs_review`
  (`recordFlags` of `packages/domain`), and `returnDecided: boolean`; the board gains
  `exceptionsToDecide: number` (FR-033). A shared domain rule selects shipments with
  `status === 'exception' && !returnDecided` for both the list and count of "Novedades por
  decidir". Counts follow the existing board's non-status filters; the displayed list also
  follows the selected status. Decided returns stay in their ordinary date section. This
  US3 projection does not add the decision actions of US4.
- **`GET /api/routes/board`**: each `RouteSummary` gains `courierLastSyncedAt` and
  `unacknowledgedNotices: number` (FR-033).
- **`GET /api/shipments/unassigned`**: also returns held shipments that are on no route, each
  with `heldBy: { courier } | 'office'`; an ordinary uncollected shipment has `heldBy: null`
  (FR-031).
- **`POST /api/routes/:id/shipments`** and **`POST /api/shipments/:id/reassign`**: accept held
  shipments; a shipment held by a courier gets only a delivery or return stop and requires a
  route in progress; one held by the office gets a pickup stop at the office first (FR-031,
  FR-041).
- **`GET /api/shipments/export`** (owner): gains the columns "Fecha de estado", "Mensajero",
  "Recibido por", "Efectivo", "Transferencia a la empresa", "Transferencia al cliente",
  "Pagos por cuenta del cliente", "Intentos", "Motivo de la última novedad" (FR-042).
- **`GET /api/export/:dataset?format=csv`** (owner): gains the datasets `courier-records`,
  `routes` (one row per stop task), and `handovers`, with Spanish headers (FR-042).
- **Every route and shipment mutation of feature 002** that affects a courier with a route in
  progress also creates a notice and sends a phone notification (FR-027, FR-040), including
  `POST /api/routes/:id/join` (`shipment_added` on the target route) and `PATCH
  /api/shipments/:id` of a shipment on the route (`shipment_updated`). `POST
  /api/routes/:id/cancel` reaches no courier: a route in preparation is not on any phone.
- **`POST /api/handovers/:id/cancel`**: a handover with no origin route (a package held off
  route) is cancelled too, leaving the shipment off route with its holder (FR-031).
- **Events** (`RouteEvent`, `ShipmentEvent`): `onBehalf` is true on the events of a record
  entered on a courier's behalf (FR-034).
  A revert that restores the original task on an in-progress route also writes a
  `RouteEvent` of type `record_reverted` with the shipment, author and reason (FR-039).
  Its occurred/recorded times are stored together with the revert; a finished route is
  not changed. `ShipmentEvent.changes` includes only values that actually changed.

## Phone notification payload (FR-040)

Push subscription endpoints must use HTTPS without URL credentials or a nonstandard port,
at `fcm.googleapis.com`, `*.push.apple.com`, or `updates.push.services.mozilla.com`.
Other destinations are `400 invalid_request` before persistence (Constitution IX, T113).

`{ type: NoticeType, routeNumber?: number }`. No names, addresses, or phone numbers.

`handover_confirmed` names confirmation by the receiving courier or dispatch; it does not
reuse `shipment_updated`, which exclusively describes an edited shipment. Both affected
couriers receive the confirmation notice (FR-027, research R9, T117).
